# 外部服务池化与负载均衡方案

> 状态：草案 · 2026-10-13
> 关联文档：[law-service-split-plan.md](law-service-split-plan.md)（法库独立化）、[deployment.md](deployment.md)（生产部署手册）
>
> 一句话方案：新建统一的**外部服务池化层** `backend/infra/service_pool/`，把 LLM API（主模型/OCP/embedding）、得理、企查查、SearXNG、法库检索服务的调用收敛为"带健康度的成员池"——多 key、多提供方加权轮询、并发闸门、客户端限流、熔断转移、统一计量，让高并发下单点上流的故障与限速不再传导为用户可见的失败。

---

## 1. 背景与目标

Lawver 的每一次对话都是一次**外部服务编排**：主模型流式调用 × 平均 4–5 轮工具循环，叠加一路 OCP 审查流，再穿插得理案例、企查查企业信息、SearXNG 联网搜索等工具外呼。单用户体感良好，但并发一上来，瓶颈全部落在出站：

- 所有 LLM 流量走**同一个 key、同一个端点**——撞上提供方限速（429）时，现有重试逻辑是指数退避后**继续打同一家**，越忙越堵；
- 任何一家提供方抖动 = 全站不可用，没有备选路径；
- 工具类外呼没有并发闸门，高峰期会把同步线程池和上游配额同时打满。

本方案的目标：

1. **故障转移**：单一 key/端点/提供方故障或限速时，自动切换到池内健康成员，用户无感。
2. **过载保护**：并发闸门 + 客户端限流，不把上游打穿（打穿上游的代价是封 key，远贵于排队）。
3. **公平性**：单个用户/会话不能耗尽整池。
4. **可观测**：每个成员的请求数、错误率、p95 延迟、在飞数可见可告警，用量计量进入现有计费体系。
5. **透明降级**：池化层自身故障时回退为现有直连行为——对齐项目里"Redis 只是防护层，连不上自动降级"的既有哲学（`.env_example` 对 `LAWVER_REDIS_URL` 的约定）。

## 2. 现状盘点

| 服务 | 传输 | 客户端生命周期 | 超时 | 重试 | 限流/闸门 | 计量 |
| --- | --- | --- | --- | --- | --- | --- |
| 主模型 LLM | async（AsyncOpenAI） | 模块单例，模型档案热切换（`function_calling.py:37,62`） | 三档：connect 10s / read 300s（字节间隔）/ write 60s，SDK 重试归零（`llm/client.py:22-24`） | `with_retry` 3 次，退避 2/4/8s，**打同一端点**（`function_calling.py:280`） | ❌ 无并发上限 | ✅ per-model 入计费 |
| OCP 审查 LLM | async | 每审查实例一个 client（`ocp.py:44`） | `OCP_CALL_TIMEOUT` | 1 次（`ocp.py` MAX_RETRIES） | ❌ | ✅ |
| embedding | urllib 直连 | 按调用 | 8s + retry_delay（`embeddings.py:191,256`） | 1 次 | ❌（有 SQLite 缓存前置） | ❌ |
| 得理案例 | **同步 requests** | **每次调用新建** client + Session，且用裸 `requests.post`（`deli_client.py:101,149`）→ 每次全新 TLS 握手 | 30s | ❌ | ❌ | ❌ |
| 企查查 | **同步 requests**（MCP SSE） | 按需构造，单 token | 30s（`qcc_client.py:207`） | ❌ | ❌ | ❌ |
| SearXNG | 同步 requests（自托管） | 模块内复用 | 20s（`SEARXNG_TIMEOUT`） | ❌ | ❌（已有引擎超时观测与全引擎失败检测，无预防闸门） | 部分指标 |
| GitHub Release 同步 | urllib | 按调用 | — | — | APK 下载 RPM 已有（`LAWVER_APK_DOWNLOAD_RPM`） | ❌ |
| 法库检索服务（[拆分方案](law-service-split-plan.md)新增） | httpx async | 待建 | 3s/10s | 1 次 | 服务端限流（key 级） | 审计日志 |

三个结构性问题：

1. **同步工具占用线程池**。得理/企查查经 `asyncio.to_thread` 执行（`agents/tool_loop.py:370`），共享默认 ThreadPoolExecutor（约 `min(32, CPU+4)` 个线程）。高峰期 30s 的外呼把线程占满，会拖累所有其他 `to_thread` 调用，且对上游完全没有并发上限——30 个并发工具调用就是 30 路同时打上游。
2. **重试语义放大拥堵**。主模型 429 后 2/4/8s 退避仍打同一 key，等于在最拥挤的时刻加第三波流量；且 3 次失败后直接对用户失败。
3. **有"多档案"、无"多成员"**。管理后台 `llm_profiles` 已支持保存多个模型档案（`settings_service.py:176,460`），但一次只激活一个——多提供方的运营基础已经存在，缺的只是池化调度。

## 3. 总体设计：统一池化层

### 3.1 分层模型

```
业务调用方（function_calling / ocp / embeddings / deli / qcc / searxng / law_service_client）
      │  pool.call(route, fn) —— 业务只声明"我要哪条 route"，不感知成员
      ▼
┌─ service_pool ──────────────────────────────────────────────┐
│ Route（有序成员列表 = failover 链）                           │
│   └─ Member（endpoint + key + weight）                       │
│        ├─ 并发闸门  asyncio.Semaphore(per-member)            │
│        ├─ 限流器    RPM/TPM 令牌桶（按 key）                  │
│        ├─ 熔断器    错误率/连续错误 → open → half-open 探测   │
│        └─ 统计      请求数/错误率/p95/在飞/429 计数           │
│   选择器：健康成员中按 (最小在飞, 权重) 挑选                   │
│   计量出口：usage → billing/metering；统计 → 管理端点          │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 三种池形态（按服务特性选型，不做一刀切）

| 形态 | 适用 | 成员含义 |
| --- | --- | --- |
| **提供方池**（重） | 主模型、OCP、embedding | 一个 OpenAI 兼容提供方（base_url + 模型 + 若干 key） |
| **凭据池**（中） | 得理、企查查 | 一个账号凭据；办不下多账号时退化为"单成员 + 闸门排队" |
| **实例池**（轻） | SearXNG、法库服务 | 一个服务实例地址（多副本预留） |

### 3.3 成员选择与负载均衡策略

- **主策略：最小在飞优先（least-in-flight），同分看权重**。对 LLM 比轮询更合适——流式调用耗时不均，最小在飞天然把新请求导向空闲成员。
- **会话粘性（可选，默认关）**：同一会话尽量粘同一成员。价值在于提供方侧的上下文缓存（DeepSeek/Qwen 的 context caching 按前缀计费命中），failover 或成员熔断时打破粘性。提供方支持前缀缓存且成本敏感时再开。
- **失败分类决定转移**，沿袭 `function_calling.py` 已有的区分：
  - **可转移**：429、5xx、连接错误、超时、首 chunk 前的流中断；
  - **不可转移**：400 参数错误、403 内容安全过滤（现有逻辑已单独识别并给出用户文案，`function_calling.py:357`）、401 凭据无效（标记成员不健康但换 key 重试一次）。
- **流式语义（关键规则）**：`chat.completions.create` 返回前的失败可安全换成员重试；**首 chunk 之后的中断不自动转移**——此时用户已收到半截回答，转移重发会造成重复输出，走现有 chat_pipeline 的用户可见降级路径，同时把该次失败计入成员健康度。

### 3.4 并发闸门、排队与公平性

- 每成员 `max_concurrency`（Semaphore）；每条 route 全局上限（所有成员之和之外再封顶，防止暴力加 key 失控）。
- 闸门满时**排队 + 队列超时**（默认 10s）：等不到成员就返回结构化错误，业务层按现有错误 JSON 模式给 agent 友好话术（"检索繁忙，请稍后重试"）。宁可快失败，不做无界等待。
- **每用户公平性**：每会话同时在飞的外呼上限（建议主模型 2 路、工具 4 路）。现有 `LAWVER_API_RATE_LIMIT`（单 IP 600/min）管的是入口请求频率，管不住"一个用户开十条流式对话占满 LLM 池"，这一层补上。

### 3.5 客户端限流（保护上游配额）

- 按 key 维护 RPM 令牌桶（LLM 提供方另有 TPM 限制的，可配 TPM 估算桶——按上次响应的 usage 滑动平均预估本次消耗）。
- 客户端限流的意义是**不要用 429 探测上游底线**：撞 429 会消耗提供方侧的配额窗口，还污染成员健康度。
- 多 worker 精度：默认进程内实现（uvicorn 多 worker 时每进程一份，限流上限按 worker 数均摊即可，误差可接受）；需要精确共享时复用 `redis_backend` 的优雅降级模式——Redis 可用则共享计数，不可用退回进程内。**不引入新的强依赖**。

### 3.6 配置模型

一个服务器本地文件（`LAWVER_POOL_FILE`，0600，永不入仓——对齐法库方案 `keys.json` 的凭据纪律）：

```json
{
  "llm": {
    "providers": [
      { "name": "provider-a", "base_url": "https://api.a.com/v1",
        "keys": ["sk-..."],
        "rpm_per_key": 600, "max_concurrency_per_key": 8, "weight": 3 },
      { "name": "provider-b", "base_url": "https://api.b.com/compatible/v1",
        "keys": ["sk-..."],
        "rpm_per_key": 300, "max_concurrency_per_key": 5, "weight": 1 }
    ],
    "routes": {
      "main":      [ { "provider": "provider-a", "model": "deepseek-v3" },
                     { "provider": "provider-b", "model": "qwen-max" } ],
      "ocp":       [ { "provider": "provider-b", "model": "qwen-turbo" } ],
      "embedding": [ { "provider": "provider-a", "model": "Qwen3-Embedding-8B" } ]
    }
  },
  "deli":    { "accounts": [ { "appid": "...", "secret": "..." } ], "rpm": 10, "max_concurrency": 4 },
  "qcc":     { "tokens": ["..."], "rpm": 5, "max_concurrency": 3 },
  "searxng": { "instances": ["http://127.0.0.1:8083"], "max_concurrency": 6 },
  "law":     { "endpoints": ["https://law-api.example.com"], "max_concurrency": 20 }
}
```

要点：

- **route 是有序列表，顺序即 failover 优先级**；只有一条 route 的服务 = 单成员池，行为退化为"闸门 + 限流"，与现状等价。
- **与模型档案的关系**：`llm_profiles` 继续是运营者在管理后台"手动选择主配置"的入口，`routes.main` 的首个成员默认对齐活动档案；池接管的是档案之上的自动调度。未配置 `LAWVER_POOL_FILE` 时一切按现状走（单档案/环境变量直连），**配置文件是纯增量选项**。
- 支持管理后台热更新 LLM keys 的既有路径，服务端文件主要承载多提供方拓扑与阈值。

### 3.7 可观测与计量

- 每成员统计（请求数/错误率/p95/在飞/429 计数/熔断状态）暴露给管理端点，管理员面板加一个"外部服务池"视图（前端 admin 面板已有先例）。
- LLM 用量计量（`billing/metering.record_model`，`function_calling.py:102`）增加 provider/key 标签，计费口径不变、归属更准。
- 告警（接现有日志/监控习惯）：某成员连续熔断、整池在飞逼近上限、p95 超阈值。

## 4. 分服务方案

### 4.1 主模型 LLM（重点）

- **起步配置**：≥2 家 OpenAI 兼容提供方 × 每家 ≥2 key。route 内的模型必须**能力对齐**（都支持 tool_calls、相近上下文窗口），否则 failover 会产生行为漂移——`function_calling.py` 已有的 DeepSeek reasoning_content 兼容分支和 tool_choice 降级分支正说明模型间差异真实存在。
- **重试语义改造**（对现有行为的唯一实质变更）：`with_retry` 的 3 次退避改为"**成员内重试 1 次 + 跨成员转移**"。现在的 2/4/8s 退避是"对同一家等三轮"，改造后是"换一家立刻试"，总耗时更短、成功率更高。`llm/retry.py` 保持原样，池层在其外。
- **超时**：沿用 `llm/client.py` 三档设计（read 300s 是字节间隔语义，流式不受影响），池层不再叠加自己的超时。
- **并发配平**：每 key `max_concurrency` 参考提供方并发条款，起步 8；池容量 = Σ(keys × per-key)，见 §5 推演。

### 4.2 OCP 审查 LLM

- 独立 route，建议指向便宜快速的小模型（审查任务是格式修复，不需要主力模型）。
- 高并发时 OCP 与主模型抢池：给 OCP route 设**独立配额上限**（如池容量的 30%），审查排队宁可慢一点，不挤占对话主链路。
- `MAX_RETRIES=1`、失败确定性回退（santizer-only）的现有策略保持。

### 4.3 得理案例检索

- **传输现代化（本方案里唯一建议动代码的传输改造）**：`deli_client.py` 的"每次调用新建 client + 裸 `requests.post`"改为模块级共享 `requests.Session`（复用连接池），或随池层直接换 `httpx.AsyncClient`。只此一处改动，消除每调用一次 TLS 握手。
- 池形态：凭据池（得理若支持多 appid 则配多账号轮询），外加 `max_concurrency=4` 闸门——工具调用是低频动作，闸门足够，不值得上复杂调度。
- 429/超时熔断后，工具返回现有结构化错误 JSON（"案例检索繁忙"），agent 会向用户转述——与 `DELINotConfiguredError` 的处理同构。

### 4.4 企查查

- 同得理：单 token + 闸门（`max_concurrency=3`）+ RPM。
- 企查查套餐有**日配额**特征：池层增加按日计数，配额耗尽 → 成员熔断至次日，工具直接返回"今日企业信息查询额度已用完"，不再空耗 30s 超时。

### 4.5 SearXNG

- 自托管服务本身不是瓶颈，**瓶颈是上游引擎按出口 IP 限流**。池化对象是这个"出口信誉"：`max_concurrency=6` 闸门压平峰值，避免并发搜索触发引擎验证码/封禁。
- 已有的引擎超时观测（`_metric("web_search.engine_timeouts")`）与全引擎失败检测保留；全引擎失败连续 N 次 → 短暂熔断 web_search 工具（返回"联网搜索暂不可用"），而不是放任每次调用都白等 20s。
- 多实例扩展（不同出口 IP 的 SearXNG 副本）留作 `instances` 列表的自然扩展，本期不部署。
- 网页抓取（`fetch`，raw socket + SSRF 防护）**不入池**，防护逻辑特殊，维持现状。

### 4.6 Embedding

- route 指向池内任一支持 OpenAI embeddings 的提供方；已有 SQLite 缓存前置，量小，配置即可，无额外改造。

### 4.7 法库检索服务

- [拆分方案](law-service-split-plan.md) 的客户端天然纳入池框架：`endpoints` 列表预留多副本，健康检查/转移逻辑复用池层，超时参数（3s/10s）保持该方案的设计。

### 4.8 GitHub Release 同步

后台低频任务，已有 token + RPM，**不入池**，仅纳入统计口径。

## 5. 高并发容量推演

一次典型对话的资源画像：工具循环平均 4 轮 → 主模型调用约 5 次，对话活跃期 60–120s，**平均在飞约 1–1.5 路主流 + 0.5 路 OCP 流**。

| 并发会话数 | 主模型在飞需求 | OCP 在飞需求 | 起步池（2 提供方 × 2 key × 8 并发 = 32）够吗 |
| --- | --- | --- | --- |
| 20 | ~25 | ~10 | ✅ 富余 |
| 50 | ~65 | ~25 | ⚠️ 主模型排队，扩 key 或降 per-session 并发 |
| 100 | ~130 | ~50 | ❌ 需 ~8–9 个 key（按 per-key 8 并发）或提高 per-key 上限 |

配平公式：`key 数 ≥ 峰值会话数 × 每会话平均在飞 ÷ per-key 并发`。闸门排队超时（10s）兜底短时峰值；持续性超出就是扩容信号，管理面板的在飞曲线会直接显示。B 端场景按**该客户部署的授权并发数**倒推 key 配置，写进部署手册。

## 6. 实施计划

| 阶段 | 内容 | 验收标准 | 粗估 |
| --- | --- | --- | --- |
| 0 池层骨架 | `service_pool/` 核心（Pool/Member/route/闸门/限流/熔断/统计）+ 配置加载 + 单测；未配置文件时全走直连 | 单测覆盖转移/熔断/排队超时/公平性；不配文件时全部现有测试原样通过 | 2–3 天 |
| 1 主模型接入 | `function_calling.py` 走池；模型档案对齐 `routes.main` 首成员；重试语义改"成员内 1 次 + 跨成员" | 主提供方人工注入 429（mock）时自动切备用提供方；403 内容过滤不转移；计费带 provider 标签 | 2 天 |
| 2 OCP/embedding | 独立 route + 配额上限 | OCP 排队不挤占 main；embedding 走池缓存行为不变 | 1 天 |
| 3 得理/企查查 | 共享 Session/AsyncClient 改造 + 闸门 + 日配额熔断 | 并发 20 路工具调用时上游侧并发 ≤ 闸门值；配额耗尽返回友好错误而非超时 | 1–2 天 |
| 4 SearXNG/法库 | 闸门 + 全引擎失败熔断；法库客户端并入池框架 | 并发搜索被压平；引擎全挂时 1 次内快速失败 | 0.5–1 天 |
| 5 可观测 | admin 池状态端点 + 面板视图 + 告警 + 压测脚本 | 面板可见每成员在飞/错误率；100 并发会话压测报告（排队率、p95、无雪崩） | 1–2 天 |

合计约 **8–11 人日**。阶段 0–1 完成即覆盖最大风险（LLM 单点），可先行上线。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 池层自身成为新故障点 | 全部出站失败 | 优雅降级为直连：池初始化失败/未配置 = 现状行为；边界测试锁定"无池配置时零行为变更" |
| 多提供方行为漂移 | failover 后回复质量/格式突变 | route 内只配能力对齐的模型；403/400 不转移；对照验收（阶段 1） |
| 前缀缓存失效 | 跨提供方转移后 token 成本上升 | 会话粘性可选；缓存敏感的部署只配单提供方多 key（key 间缓存通常不共享，粘性同样按 key） |
| 同步工具线程池仍可能被慢外呼占满 | 其他 `to_thread` 受拖累 | 闸门先行减少无效占用；观察阶段 3 压测，必要时 deli/qcc 迁 async httpx（列入后续迭代） |
| 多 key 泄露面扩大 | 凭据风险 | 凭据只存服务器本地文件/管理后台，永不入仓；per-key 可独立禁用 |
| 客户端限流与提供方实际配额不符 | 误判成员不健康 | 配置项按提供方账单页校准；429 只降健康度不立即熔断 |
| 计费归属混乱 | 对账困难 | provider/key 标签随 usage 入 metering（阶段 1 同步做） |

## 8. 备选方案说明：自托管 LLM 网关

社区方案（one-api / new-api / LiteLLM proxy）提供开箱即用的多 key 轮询与 failover，部署一个即可覆盖 §4.1–4.2 的 LLM 部分。**本方案仍推荐自研薄池层**，理由：与现有"模型档案热切换、计费 metering、流式超时语义、OCP 独立重试策略"的衔接是点对点的，而网关需要在网关侧重配这些语义、多一跳延迟与一个新运维对象；且工具类服务（得理/企查查/SearXNG）网关不覆盖，池层终归要做。**触发重评估的条件**：接入提供方 >5 家、需要租户级配额隔离（多 B 端客户共享一套我方网关）时，网关方案的成本优势会反转，届时再议。

## 9. 范围外事项

- **跨机/跨地域负载均衡**：单机部署内的问题，多机容灾属 deployment.md 层面（主备/双活另立方案）。
- **计费模型变更**：本方案只给计量加标签，不改计费规则。
- **LLM 提供方商务谈判/多开账号**：池层的技术前提，凭据获取属运营动作。
- **得理/企查查异步化重构**：本期只做连接复用与闸门，全 async 迁移视压测结果列入后续迭代。
